
# Runtimes in detail

> [!NOTE]
>
> This section is only useful if you want to learn more, or if you want to use Bref with a deployment tool other than the serverless CLI.
>
> You can skip it for now if you just want to get started with Bref.

## AWS Lambda layers

Bref runtimes are distributed as [AWS Lambda layers](https://docs.aws.amazon.com/lambda/latest/dg/configuration-layers.html). While Bref provides a Serverless plugin to simplify how to use them, you can use the layers directly.

The layer names (aka "[ARN](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference-arns.html)") follow this pattern:

```
arn:aws:lambda:<region>:873528684822:layer:<layer-name>:<layer-version>
```

For example:
```
arn:aws:lambda:us-east-1:873528684822:layer:php-84:25
```

There is one layer per PHP version (`php-82` to `php-85`, and `arm-php-82` to `arm-php-85` for ARM functions). The same layer runs all Bref runtimes: the `BREF_RUNTIME` environment variable selects the runtime, and the function's `handler` has a different meaning for each:

| `BREF_RUNTIME` | Runtime | `handler` |
|----------------|---------|-----------|
| `fpm` | [PHP-FPM runtime](./fpm-runtime.mdx) for web applications | the PHP file that receives HTTP requests, for example `public/index.php` |
| `function` | [Event-driven functions](./function.mdx) | a PHP file that returns the handler, for example `index.php`, or a class name resolved from the [DI container](./function.mdx#di-container-integration) |
| `console` | [Console runtime](./console.mdx) | the CLI script to run, for example `bin/console` or `artisan` |

When `BREF_RUNTIME` is not set, the function fails on every invocation with "The environment variable `BREF_RUNTIME` is not set".

You can use layers via their full ARN, for example in `serverless.yml`:

```yml filename="serverless.yml" {9,10,11}
service: app
provider:
    name: aws
functions:
    hello:
        handler: public/index.php
        runtime: provided.al2023
        layers:
            - 'arn:aws:lambda:us-east-1:873528684822:layer:php-84:25'
        environment:
            BREF_RUNTIME: fpm
```

Or if you are using [SAM's `template.yaml`](https://aws.amazon.com/serverless/sam/):

```yml filename="template.yml"
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Resources:
    Hello:
        Type: AWS::Serverless::Function
        Properties:
            # ...
            Handler: public/index.php
            Runtime: provided.al2023
            Layers:
                - 'arn:aws:lambda:us-east-1:873528684822:layer:php-84:25'
            Environment:
                Variables:
                    BREF_RUNTIME: fpm
```

Bref layers work with AWS Lambda regardless of the tool you use to deploy your application: Serverless, SAM, CloudFormation, Terraform, AWS CDK, etc.

> [!WARNING]
>
> Remember: the layer ARN contains a region. **You need to use the same region as the rest of your application** else Lambda will not find the layer.

## Environment variables

Bref exposes the following environment variables on every Lambda invocation, in all runtimes:

- **`LAMBDA_REQUEST_ID`**: the current AWS Lambda request ID. This is useful for logging and tracing purposes, for example to group all logs of the same invocation.
- **`_X_AMZN_TRACE_ID`**: the [AWS X-Ray](https://docs.aws.amazon.com/lambda/latest/dg/services-xray.html) trace ID. This is a standard AWS Lambda variable that is normally set by native runtimes.
- **`LAMBDA_INVOCATION_CONTEXT`**: the [Lambda context](./fpm-runtime.mdx#lambda-context) as a JSON-encoded string.

The PHP-FPM runtime also exposes **`LAMBDA_REQUEST_CONTEXT`**: the [API Gateway request context](./fpm-runtime.mdx#request-context) as a JSON-encoded string.

These variables are refreshed on every invocation.

The Bref plugin for `serverless.yml` sets these variables on deployment:

- **`BREF_RUNTIME`**: the runtime to start, set from `runtime: php-xx`, `php-xx-fpm` or `php-xx-console`. Set it yourself (`fpm`, `function` or `console`) when you use the layers (see [above](#aws-lambda-layers)) or the [Docker images](/docs/deploy/docker.mdx) directly.
- **`BREF_STACK_NAME`**: the name of the CloudFormation stack (see [Variables set by Bref](/docs/environment/variables.mdx#variables-set-by-bref)).

You can set these variables to change how Bref behaves:

- **`BREF_LOOP_MAX`**: the number of invocations a PHP process handles before restarting (default: 1). See [keeping the PHP process alive](/docs/environment/performances.mdx#bref-for-event-driven-functions).
- **`BREF_AUTOLOAD_PATH`**: the path to Composer's `autoload.php` if the `vendor` directory is not at the root of the project (see [Custom vendor path](/docs/environment/php.mdx#custom-vendor-path)).
- **`BREF_BINARY_RESPONSES`**: set to `1` to return binary HTTP responses (see [Binary requests and responses](/docs/use-cases/http/binary-requests-responses.mdx)).
- **`BREF_PING_DISABLE`**: set to `1` to disable the [telemetry ping](#telemetry-ping).

## Telemetry ping

Bref's runtime (the `bref/bref` Composer package) sends an anonymous ping to estimate the total number of Lambda invocations powered by Bref. That statistic is useful in two ways:

- to provide new users an idea on how much Bref is used in production
- to communicate to AWS how much Bref is used and push for better PHP integration with AWS Lambda tooling

We consider this to be beneficial both to the Bref project (to get more users and more consideration from AWS) and for Bref users (more users means a larger community, a stronger and more active project, as well as more features from AWS).

So far, knowing the number of Bref invocations has helped Bref grow, be recognized by AWS, and opened a lot of doors.

### Data

You can find the latest number of AWS Lambda invocations on the [Bref homepage](https://bref.sh/).

On the month of the Bref 1.0 release, [Bref was powering 1 billion invocations per month](../../news/01-bref-1.0.md#1-billion-executions-per-month).

On the month of the Bref 2.0 release, [Bref was powering 10 billion invocations per month](../../news/02-bref-2.0.md).

On the month of the Bref 3.0 release, [Bref was powering 40 billion invocations per month](../../news/03-bref-3.0.mdx).

### What is sent

The data sent in the ping is completely anonymous. It does not contain any identifiable data about anything (the project, users, etc.).

**The only data it contains is:** A Bref invocation happened with the runtime XYZ (where XYZ is the name of the Bref runtime, like "function", "fpm" or "console") and whether the invocation was a cold start.

Here is an example payload:

```
Invocations_100:1|c\nLayer_fpm_100:1|c\nCold_100:1|c\nWarm_100:0|c
```

Anyone can inspect the code and the data sent by checking the [`Bref\Runtime\LambdaRuntime::ping()` function](https://github.com/brefphp/bref/blob/master/src/Runtime/LambdaRuntime.php).

### How is it sent

The data is sent via the [statsd](https://github.com/statsd/statsd) protocol, over [UDP](https://en.wikipedia.org/wiki/User_Datagram_Protocol).

Unlike TCP, UDP does not check that the message correctly arrived at the server.
It doesn't even establish a connection. That means that **UDP is extremely fast**:
the data is sent over the network and the code moves on to the next line.
When actually sending data, the overhead of that ping takes about 150 micro-seconds.

However, this function actually sends data in 1% of invocations (picked at random), because we don't
need to measure *all* invocations. We only need an approximation.
That means that 99% of the time, no data is sent, and the function takes 30 micro-seconds.
If we average all executions, the overhead of that ping is about **31 micro-seconds**.

Given that it is much much less than even 1 milli-second, we consider that overhead negligible.

### Disabling

The ping can be disabled by setting a `BREF_PING_DISABLE` environment variable to `1`.

> [!TIP]
>
> If your company policy requires disabling the ping, it would be extremely beneficial to the project (and transitively to your company) to report privately a rough number of invocations. You can send me a direct email at [matthieu@bref.sh](mailto:matthieu@bref.sh).
>
> Such data is collected privately and is not shared publicly on its own. I include it in the total number of invocations that I share publicly.

## Deployment telemetry

The Bref plugin for `serverless.yml` sends an anonymous UDP packet every time a `serverless` command runs (including when `bref deploy` runs it). It is used to estimate the number of Bref users and which commands are used the most.

The packet contains: the command (for example `deploy`), the Bref major version, whether the command runs in CI, the anonymous ID and installation date created by the `serverless` CLI, the timezone, the types of [Lift](https://github.com/getlift/lift) constructs used, and the names of the [extra PHP extension](/docs/environment/php.mdx#extra-extensions) layers used. Anyone can inspect the code in the `telemetry()` method of [Bref's `index.js`](https://github.com/brefphp/bref/blob/master/index.js).

To disable it, set the `SLS_TELEMETRY_DISABLED` environment variable to `1` on the machine that runs the deployment.
